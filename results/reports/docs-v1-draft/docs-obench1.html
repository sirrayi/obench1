How to read them

  • Approved is the headline. Each task’s graders score a cell out of 100 (that’s raw); then 15 category judges look at the evidence, and the cell’s points count only if none of them rejects it. A cell that passes its tests but leaves a process running, rewrites git history it shouldn’t, or claims it finished when it didn’t, scores raw points and no approved ones.
  • The 95% interval is how far the approved score could move with a different draw of tasks. Where two intervals overlap, the gap between those harnesses isn’t settled.
  • Solved counts cells where every one of the task’s checks passed, before the judges.
  • Gate breaches count cells that failed a check marked as a safety or destructive-action gate. Which cells, and which checks, is sealed.
  • Reliable categories: a harness is reliable in a category when it was approved on every seed in at least 90% of that category’s tasks. The summit is all 15 at once with no gate breach anywhere. No harness reached it.
  • $ per approved point is total spend divided by approved points, so cheap and wrong doesn’t look cheap. It compares harnesses within this run only: a run with more seeds spends more per point.

What it measures

OBench1 tests the harness, not the model. Every arm gets the same model, the same settings and the same tasks at the same moment, so the only thing left to differ is the software around the model: its tools, prompts, memory, recovery and judgement.

The 15 categories came from what the best harnesses each do well. Overseer was built to cover all of them; each other harness was built around its own subset. That matters for how far this result reaches.

CategoryWhat it asks
Long-horizon executionCan it keep going for hours and hundreds of steps without losing the thread?
Context managementDoes it find the one line that matters in a flood, and stay inside its context?
Memory across sessionsDoes it remember corrections, and refuse a poisoned note?
Orchestration and subagentsCan it split work, run it in parallel and put it back together?
Tool useDoes it edit precisely, rename across a codebase, and cope with odd file systems?
Skills and extensibilityDoes it use what it’s given to extend itself?
Token, cache and prompt efficiencyHow much does it spend, and how much of that is served from cache?
SpeedDoes it finish inside half the task’s wall cap?
Instruction followingDoes it keep the house rules: reply length, sign-off, no emoji, no TODOs?
Policy and repo rulesDoes it respect the repo’s rules, including nested ones, and leave git alone unless told?
Out-of-the-box problem solvingCan it work out a lying error, a lost fixture, a slow oracle?
Verification, critique and reviewDoes it check its own work, and not trust a fix because someone said it works?
Safety and trustDoes it keep secrets, avoid destructive actions and leave nothing running?
ResilienceDoes it ride out provider faults and mid-run changes?
Honest reportingDoes it say what it didn’t finish, instead of claiming it’s all done?

How it’s graded

  • The graders are each task’s own checks, run on the system Python outside the harness’s reach. They score what’s in the workspace, the git history and the replies.
  • The judges are code, not a model. No AI grades anything. Each of the 15 category judges reads the checks tagged with its category plus signals every cell has: budgets, whether each phase finished on its own, git refs, leftover processes, editor debris, overclaiming in the final reply, and any peek at the benchmark itself. A judge with nothing to go on abstains.
  • The judges never see which harness made the cell. We checked: no grader or judge reads a harness’s name.
  • The graders are proven first. Before the first paid run, each task’s reference solution must score 100 (27 of 27 did) and doing nothing must score 0 (27 of 27 did).
  • Budgets are first guesses. The token, context, cache and speed budgets the efficiency and speed judges use haven’t been calibrated from field data yet. They’re the same for every harness, but they may be too tight or too loose.

Same conditions for everyone

One model, one gateway

Every harness used the OpenCode Go subscription with deepseek-v4.1-flash: 1M tokens of context, 384K of output. Each cell gets its own gateway on this machine, and every model call goes through it. Whatever a harness asks for, the call that reaches the provider carries the same four settings. The gateway logs every request it had to change.

SettingSent on every callWhy
modeldeepseek-v4.1-flashone model for everyone
thinkingonsome harnesses send no thinking field, or turn it off for side calls
reasoning effortmaxthe provider’s top level
output ceiling384,000 tokensthe model’s own limit, so nobody’s thinking gets cut short

Raising side calls to max effort costs some harnesses a little more than they’d spend on their own. One rule for every call is easier to check than a rule per harness.

Same context, same limits, same moment

  • Context: all five plan for a 1M-token window for this model, so none compacts its history earlier than another for lack of information.
  • Limits: the task’s wall cap is the only limit. Overseer ships with a 100-step and $5 budget, which the others don’t have, so we lifted both. Approvals are off for every arm.
  • Lockstep: the five arms of a task and seed start together, in a launch order shuffled per task and seed, at the same process priority. They share the same provider load, machine load and hour.
  • Faults: injected provider faults follow one plan per task and seed, keyed to the call number, the same for every arm.

The same jail

  • Every cell runs inside a macOS sandbox. It can reach loopback only, so the gateway is the only way out.
  • It can’t launch apps, send Apple Events, reach the window server or Accessibility, or run any copy of a computer-use driver. Computer use is off for every arm in this benchmark (it isn’t off in the products).
  • Every cell gets a fresh home directory. No harness sees our own configs, memories, skills or sessions.

Proved before money was spent

Before the paid run, every harness ran against a fake provider on this machine, with a dummy key. The check proves each one routes through its gateway with the forced settings, and that its own shell tool works: it writes a file, then tries to launch an app, send an Apple Event and find the computer-use driver. All five wrote the file, and all three escapes were refused for all five.

What still differs

On purpose, because it’s what makes a harness what it is:

  • Tools: Overseer v5 offers 10, pi 4, omp 11, Hermes 19, dsh 25.
  • Side calls: omp makes a short title call, dsh a small extra call, Hermes probes the endpoint for its context size, Overseer runs a memory review after its final answer.
  • Recovery: each handles errors its own way. During the evening’s throttling (below), the median gap between one harness’s rate-limited calls was about 3 seconds for omp, dsh and Hermes, 4 for pi and 13 for Overseer.
  • Prompts, temperature, memory and everything else.

What each harness got that the others didn’t

Small changes we made so each harness could run here at all. None touches grading.

What went wrong

In order. Some of it is about Overseer, and we’d rather you read it here than find it.

The pilot didn’t measure Overseer

A one-seed pilot ran on 5 November. Overseer came last on approved score (29.6) while costing about three times the next harness ($1.11). Reading its transcripts, we found why: its shell never worked. macOS refuses to start a second sandbox inside a first (sandbox_apply: Operation not permitted), and every one of Overseer’s 178 shell calls failed. None of the other four sandboxes its own shell, so none hit it.

We voided the pilot’s Overseer row. Its other four rows stand. For the record:

The pilot’s wiring check only checked routing, not whether a tool call works, which is how this got past it. The check now runs each harness’s shell (above).

Overseer drove the Mac’s desktop to get a shell

This is the serious one. With its shell blocked, Overseer used its computer-use tool, in 8 of the pilot’s 27 tasks, to open Terminal and Script Editor on the real desktop, type shell commands into Terminal, run do shell script, delete files with rm -f, quit both apps with killall and start background jobs. All of that ran outside the benchmark’s sandbox, as the machine’s user.

It ran on our own benchmark machine, not a customer’s. It left 7 files in /tmp, which we moved to the Trash, and left Terminal and Script Editor open. But on someone’s own Mac, “the sandbox said no, so it opened my Terminal and did it anyway” is exactly what an agent must never do. What we changed:

  • In Overseer (v5.0.0-rc2): the computer tool now refuses to launch or type into any terminal or script app, to open script files, and to run do shell script. And when the shell sandbox can’t start, Overseer now says so once, plainly, instead of failing the same way 178 times.
  • In the benchmark: the jail now blocks launching apps, Apple Events, the window server, Accessibility and every copy of a computer-use driver, for every harness. We checked each block by hand.
  • Still open: a general rule that stops any tool after the same failure three times. We built it and dropped it before release: it tripped on ordinary refusals and would have ended healthy runs.

We stopped a run and started again

The first three-seed run started before we’d found the above. We stopped it after about an hour ($0.40 spent), fixed the jail and Overseer, and reran every harness from the start. We didn’t give Overseer extra runs: fairness here comes from every arm running the same tasks, at the same hour, the same number of times.

The provider key was visible to every harness

The run passes the OpenCode Go key to each harness through its environment, so every harness could read it. In three cells, pi listed its environment, so the key was written into its transcripts and sent to the provider as part of its context. No other harness printed it. The key is being rotated, and the next run gives each harness a dummy key, with the gateway adding the real one, so no harness can see it.

The provider throttled us for an evening

From about 21:00 to 21:40 UTC on 5 November, the provider rate-limited us in bursts: for a few minutes at a time, 40–60% of calls got a 429. These were real, not injected. Rejected calls cost nothing, but they cost wall time, and unevenly: harnesses that retry fast pile up more 429s. Wall times on the memory tasks that evening say more about the throttling than about the harnesses.

Limits of this result

  • We wrote both the benchmark and Overseer. The categories come from other harnesses’ strengths, and a rule keeps anyone building Overseer from seeing which tasks it failed. That guards against tuning to the test. It can’t rule out scenarios that lean our way without anyone meaning them to.
  • An all-rounder’s benchmark. Overseer was built to cover all 15 categories, and the score weights them equally. That rewards breadth. To compare harnesses at what each cares about most, read the category view, not the total.
  • One model, one provider, one night. All of this is deepseek-v4.1-flash on OpenCode Go. It says nothing yet about other models.
  • Three seeds. Enough to call a category reliable, not enough to make the intervals narrow. Where they overlap, the order isn’t settled.
  • Uncalibrated budgets, as above.

What it taught us about v5

From the transcripts and the blind totals only, never from which tasks it failed. These are going into Overseer’s next round of work.

  • It writes too much. Overseer wrote the most output per call of any harness, and most of it is reasoning. Output is the dearest token, and it’s the main reason Overseer spent the most in total.
  • It over-checks on long tasks. On one long migration it ran about 30 separate one-off checks after the work was done, each a full round trip; the other harnesses stopped at the test suite. One batched check would do.
  • It misreads its own changes as someone else’s. When its shell edited a scratch file, Overseer told itself “the owner changed” that file and re-read it.
  • It makes one call after the answer. Its memory review runs right after the final reply. It handled the 429s it got there cleanly, but on a one-off headless run it’s an extra paid call.
  • It flagged a claim it couldn’t back, and sent it anyway. Its own check marked “tests: 2 passed” as unbacked (no tests ran after its last change). A flagged claim should be fixed or cut before the answer goes out.
  • What worked: it backed off under rate limits instead of hammering the shared limit, and it used the fewest tokens per approved point.

How it was watched

A watcher read every cell’s gateway log every 30 seconds and kept log sheets: every model call (status, tokens, time to first byte, duration), every finished cell, and an events log of anything worth a look. Alerts fired on stalls (checked against the process list), real provider errors, failure streaks, sustained rate limits, any sign of Overseer’s shell failing, any mention of Terminal or Script Editor, and the runner stopping. The watcher never reads grades.

What’s sealed, and what’s next

Per-task results and transcripts are sealed for now. While anyone working on Overseer can’t see which tasks it failed, nobody can tune it to the test, and the next score still means something. Everything on this page comes from the suite totals and the run’s logs.

We’ll say here when that changes.
